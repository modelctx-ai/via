# 性能基准结果（0.1）

由 `npm run bench:perf` 生成，方法见 [测试与评测](../../docs/development/testing.md#性能基准)。对照的目标在同一文档的「性能目标」。下面的表是一次完整运行（30 次测量 + 5 次预热）的原始输出，挑选并加了说明；评测机是共享的虚拟机，同机其他任务会让 p95 抖动，所以结论只看中位数的量级和前后对比，不看个位数的毫秒。

## 环境

- CPU：Intel Xeon @ 2.80 GHz，4 核（虚拟机），内存 15.7 GiB
- OS：Linux 6.18.44 x64
- Node.js v22.22.0；Bun 1.4.2
- 场景：8 个真实 `tools/list` 快照（github、linear、notion、slack、gmail、filesystem、exa、postgres，共 180 个工具）写入磁盘缓存后，server 全部停止；HOME 与 TMPDIR 在临时目录里，不读取任何真实的框架配置；除第 5 节外都设 `VIA_NO_DAEMON=1`
- 被测构建：`dist/`（含本次附带的两项构建与渲染改动，见下），对照构建：同一份源码、只去掉这两项改动

## 结论

| 目标 | 实测（中位数） | 结果 |
| --- | --- | --- |
| CLI 冷启动 < 80 ms：`--version` / `-h`（缓存热） | 43.5 / 41.1 ms，比裸 `node -e 0`（33.6 ms）多约 8–10 ms | 达标 |
| CLI 冷启动 < 80 ms：`via` / `via <provider>` / `via find`（缓存命中，180 个工具） | 107.7 / 104.4 / 118.3 ms（裸 node 之上约 70–85 ms） | **未达标** |
| 1,000 个工具上的 `find` < 30 ms：常驻索引上的查询 | 0.41 ms | 达标 |
| 1,000 个工具上的 `find` < 30 ms：一次性进程里的 目录构建 + 索引 + 首次查询 | 96.1 ms（构建 66.2 + 索引 25.5 + 查询 2.1） | **未达标**（0.1 无 daemon，每次 `find` 都要付） |
| 经热 daemon 调用的额外开销 < 15 ms（相对复用连接的 SDK 调用） | 5.8 ms（进程内 `run()` 7.1 ms，SDK 1.3 ms） | 达标 |
| daemon 常驻内存 < 80 MB（不含 stdio 子进程） | 空闲 58.2 MiB；一个 HTTP 会话后 83.0；再加 stdio 会话后 89.2；多次调用后回落到 75.1 | 空闲达标，建立会话后**略超** |

附带改动的前后对比（同一场景，缓存热，中位数，ms）：

| 项 | 之前 | 之后 |
| --- | ---: | ---: |
| `via`（根视图） | 185.8 | 107.7 |
| `via github` | 161.9 | 104.4 |
| `via find "create issue"` | 191.0 | 118.3 |
| `via doctor`（对着运行中的 server） | 449.8 | 415.9 |
| `via gh echo_text`，无 daemon，整进程 | 587.8 | 458.7 |
| `via gh echo_text`，经热 daemon，整进程 | 191.1 | 151.7 |
| daemon 空闲 RSS（MiB） | 63.0 | 58.2 |
| daemon 建立 HTTP 会话后 RSS（MiB） | 95.9 | 83.0 |
| `--version` / `-h` | 50.2 / 43.0 | 43.5 / 41.1（差异在噪声内） |

两项改动（各自一个提交，各带不依赖时间的测试）：

1. **依赖打进分块**（`perf(build)`）。运行时依赖原先是外部包，`yaml`、ajv、MCP SDK 各是数十到数百个要逐个解析、读取的文件：单独 `import('yaml')` 约 30 ms，打包后约 6 ms。现在除原生的 `@napi-rs/keyring` 外都打进各自的懒加载分块（CommonJS 依赖经动态 `import()` 只有 `default`，配置解析按此兼容）。这也与规范里「单文件」的假设一致。
2. **表格宽度的 Unicode 初始化推迟**（`perf(render)`）。`string-width` 在模块加载时创建 `Intl.Segmenter` 并编译 `\p{RGI_Emoji}` 正则，约 30 ms；浏览视图里几乎只有 ASCII 和 `·`、`…`、`→` 这类窄字符。`src/render/terminal-width.ts` 是同一算法，窄字符直接按长度计，其余情况才初始化；`string-width` 退为开发依赖，只在测试里当一致性参照。

## 1. 冷启动

`node -e 0` 基线 33.6 ms（p95 46.2，最小 26.9）。「缓存热」是发布形态：入口在决定需要命令运行器之后才调用 `module.enableCompileCache()`。

| 命令 | 无缓存 | 缓存冷（每次新目录） | 缓存热 | 缓存热 − 基线 |
| --- | ---: | ---: | ---: | ---: |
| `--version` | 44.1 | 42.4 | 43.5 | 9.9 |
| `-h` | 42.4 | 42.0 | 41.1 | 7.5 |
| `via` | 115.9 | 127.6 | 107.7 | 74.2 |
| `via github` | 118.1 | 141.0 | 104.4 | 70.8 |
| `via find` | 122.7 | 147.9 | 118.3 | 84.8 |
| `via doctor`（8 个运行中的 server） | 433.6 | 508.5 | 415.9 | 382.3 |

- 编译缓存对代码很小的路径几乎没有收益（`--version` 在噪声内持平）；它帮得上的是浏览类命令里较大的分块，缓存热比无缓存快约 5–10%，首次运行（缓存冷）反而慢约 10–20 ms（要写缓存）。`--version` / `-h` 本来就不经过 `enableCompileCache()`；用环境变量 `NODE_COMPILE_CACHE` 让入口也走缓存，没有可见收益。
- 「单文件」：目标写的是单文件，实际是 `dist/via.js` 加按需加载的分块，`--version` 只加载 4 个分块共 7 KiB。没有必要合并成真正的单文件。
- 浏览类命令剩下的约 75 ms（装载 yaml 约 13、目录规则与数据各约 8、GC 约 7、模块实例化若干，CPU profile 的量级，未逐项优化），其中一半以上是每个进程都要重做的配置解析与目录构建，只有 daemon 或更激进的缓存才能省掉。
- `doctor` 需要连接每个 server，比较的是并发探测，不是启动。

## 2. 1,000 个工具上的 `find`

合成目录由 `scripts/lib/synth-catalog.ts` 生成：把 23 个夹具 provider 克隆成 50 个，工具名与描述用固定种子扰动，同样的参数在任何机器上得到同样的 1,000 个工具。

| 阶段 | 新进程里的首次调用 | 稳态（常驻） |
| --- | ---: | ---: |
| 目录构建（拆分、分域） | 66.2 | 32.3 |
| 索引构建 | 25.5 | 16.8 |
| 查询（取前 10） | 2.11 | 0.41 |
| 渲染命中 | 1.06 | - |
| 构建 + 索引 + 首次查询 | 96.1 | 49.5 |

首次调用和稳态的差距主要是 JIT 预热。每个工具的构建加索引成本约 0.1 ms（一次性进程）。查询本身不是问题，一次性进程的构建才是；0.1 的真实目录（一般几十到几百个工具）下，这部分是 5–25 ms。

## 3. 调用开销（无 daemon）

| 场景 | 中位数 ms |
| --- | ---: |
| 进程内：SDK `callTool`，复用连接 | 1.68 |
| 进程内：SDK 新建连接 + `callTool` + 关闭 | 6.26 |
| 进程内：`run([gh echo_text …])` | 34.2 |
| 整进程：`node -e 0` | 35.5 |
| 整进程：`node` 只跑 SDK client 的脚本（同样启用编译缓存） | 338.7 |
| 整进程：`node dist/via.js gh echo_text` | 458.7 |

- 进程内 via 比新建连接的 SDK 调用多约 28 ms（配置读取、目录缓存、参数校验、渲染，JIT 已热）。
- 整进程里，加载 MCP SDK 本身要 300 多 ms（只做 `Client.connect` + `callTool` 的最小脚本），via 在此之上再加约 120 ms。无 daemon 时一次调用的绝大部分是加载 SDK，这是 0.2 daemon 的理由：经热 daemon 的整进程调用降到 151.7 ms，因为 CLI 进程既不加载 SDK 也不加载 ajv。

## 4. 每条命令加载了什么

| 命令 | 分块 | KiB | 其中的库 |
| --- | ---: | ---: | --- |
| `--version` | 4 | 7 | 无 |
| `-h` | 4 | 7 | 无 |
| `via` | 35 | 470 | yaml、jsonc-parser（所在分块共用） |
| `via github` | 38 | 537 | 同上 |
| `via find` | 35 | 471 | 同上 |
| `via doctor` | 42 | 1161 | ajv、mcp-sdk、zod、yaml、jsonc-parser |
| `via gh echo_text` | 51 | 1250 | 同上 |

`--version` 与 `-h` 不加载任何库，命中缓存的浏览命令不加载 MCP SDK、zod 和 ajv。这两条在脚本里和 `test/cli/dist.test.ts` 里都有断言。

| 进程内：SDK `callTool`，复用连接（下限） | 1.31 |
| 进程内：`run()`，无 daemon | 39.1 |
| 进程内：`run()`，经热 daemon | 7.10 |

| 整进程：`via gh echo_text`，无 daemon | 553.6（本次运行；表 3 的另一次为 458.7） |

| daemon 常驻内存 | RSS MiB |
| --- | ---: |
| 刚启动，没有会话 | 58.2 |

## 6. Bun（运行时与分发的开放问题）

单位 ms，中位数；Bun 1.4.2，同一个场景和同一份磁盘缓存。`bun -e 0` 基线 7.7，`node -e 0` 为 41.3（该次运行）。

| 命令 | `node dist/via.js`（缓存热） | `bun dist/via.js` | `bun build --compile` 单文件（85 MiB） |
| --- | ---: | ---: | ---: |
| `--version` | 44.2 | 28.3 | 72.1 |
| `-h` | 49.4 | 25.6 | 77.5 |
| `via` | 122.2 | 81.9 | 120.4 |
| `via find` | 120.0 | 88.8 | 121.2 |

- Bun 作为**运行时**跑同一个 `dist/via.js` 更快：`--version` 快约 35%，浏览类命令快约 25–30%。
- Bun 的**单文件可执行**在这台机器上并不比 Node 22 + 编译缓存快：浏览类命令持平，`--version` / `-h` 反而慢约 30 ms（85 MiB 的二进制自身的加载成本，最小值也有 63 ms）。
- 单文件版本只测了启动，没有验证钥匙串绑定、stdio 子进程等路径；`bun build --compile` 能成功打出，不代表所有功能可用。
- 因此冷启动一项不构成「以 Bun 单文件为主要分发形式」的理由；它支持的结论是：若要把 Bun 作为可选运行时，收益来自 Bun 运行时本身，而不是打成单文件。该问题保持开放，免装 Node 的需求另当别论。
- **0.3 更正**：上面是不带任何标志的 `bun build --compile`。[perf-0.3](perf-0.3.md) 查明了慢的原因（每次启动重新解析整包 JS，而不是 85 MiB 的体积）：加上 `--bytecode` 与 `--splitting` 后，单文件是所有形态里最快的，这一节「冷启动不构成理由」的结论不再成立。

## 校准建议（不改规范里的目标）

1. **冷启动**：把目标拆成两档。`--version` / `-h` 保持 < 80 ms（实测约 43 ms，可收紧到 < 60 ms）；缓存命中的浏览命令（`via`、`via <provider>`、`via find`，约 200 个工具以内）定为 < 120 ms，当前约 105–120 ms，有余量的优化方向是配置解析（yaml）和目录构建的数据加载。
2. **`find` 1,000 个工具**：写明测的是哪一段。常驻索引上的查询实测 0.4 ms，< 30 ms 太松，可收紧到 < 5 ms；一次性进程的 构建 + 索引 + 查询（0.1 的真实情况）约 96 ms，另列一项，如 < 120 ms，并在 0.2 评估 daemon 是否常驻目录索引。
3. **热 daemon 开销**：测量口径需要写明——相对「复用连接的 SDK 调用」，5.8 ms，达标；整进程一次调用约 150 ms，其中约 35 ms 是裸 Node 启动，约 80 ms 是 CLI 的冷启动，与 daemon 无关。
4. **daemon 内存**：空闲 58 MiB 达标；一旦建立会话并加载 MCP SDK、ajv、zod，约 83–89 MiB，超出 80 MB。要么把目标改成 < 100 MB（会话已建立），要么继续减小（例如 ajv 与 zod 的加载按需、daemon 不加载暂时用不到的部分）。打包依赖已经让它降了约 13 MiB。

## 局限

- 虚拟机、共享 CPU：p95 与最小值受同机其他任务影响，前后对比用的是同一次会话里交替运行或相邻运行的中位数；个位数毫秒的差异不要当真。
- 磁盘缓存场景用 8 个 provider、180 个工具；工具更多时浏览类命令的构建成本按表 2 线性增长。
- 进程内的调用开销是 JIT 已热的数字；整进程的数字才是一次性 CLI 的真实体验。
- 合成目录按夹具扰动，名字分布与真实 server 不完全相同，只用于计时和确定性检查，不用于评价拆分质量。
- Bun 的单文件只测了启动。
