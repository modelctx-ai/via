### 换个算法会怎样

总览按任务要求，把 via、mcp2cli 与 mcpc 的说明文本只算一次，native 的工具定义按每轮算。两边的口径可以各换一种：

- **说明常驻每一轮**：说明放在 AGENTS.md 或 skill 里，和工具定义一样随每轮请求发送（提示缓存降低费用，但不改变占用的上下文）。按「说明 × 轮数」重算。
- **native 不计注入**：框架对工具定义做延迟加载或检索时，每轮注入接近零，但调用和原始结果仍在。这一行只剩调用与原始结果，不含发现成本，所以偏低。

|  | native | via | mcp2cli | mcpc |
| --- | ---: | ---: | ---: | ---: |
| 总览（说明算一次） | 382,379 | 15,365 | 60,152 | 57,691 |
| 说明常驻每一轮 | 382,379 | 26,573 | 296,953 | 256,550 |
| native 不计注入 | 15,813 | 15,365 | 60,152 | 57,691 |

## 这些数字说明什么

**说明的**：同一组任务、同一批 server 之下，各种方式放进模型上下文的内容量级差异——原生注入的每轮固定成本，via 的说明加按需发现与紧凑渲染，mcp2cli 的说明加平铺列表与原样 JSON，mcpc 的说明加建会话、工具列表与保持 MCP 形状的结果。命令文本和 stdout、stderr（含元信息行）都是真实运行 `dist/via.js` 得到的字节数，不是估计的。

**不说明的**：

- 任务成功率、错误调用和发现轮数。via、mcp2cli 与 mcpc 的命令序列是人按「合理的 agent 路径」写的脚本，不是模型的实际行为；真实模型会多走弯路，也可能少走。这部分由 agent 评测验证（[测试与评测](../../docs/development/testing.md#agent-评测)）。
- 精确的 token 数。这里只做 4 字节约 1 token 的估算；代码、中日韩文本或标点密集的 JSON 的实际比例不同，各列的偏差方向也不一定一致。比较的是量级和比例，不是计费。
- 夹具有一部分是合成的（见 [test/fixtures/README.md](../../test/fixtures/README.md)）。工具名取自真实 server，但描述和参数已精简、没有逐参数的说明文字，所以 native 的注入成本是**偏低**估计：真实的 GitHub、Notion 的 `tools/list` 要大得多。
- `tools/call` 的结果是按常见 API 的形状合成的（`bench/recordings/`）。via 在结果侧的节省取决于 server 返回的 JSON 有多冗余；已经精简输出的 server 上差距会小得多。文本型结果（源码文件、页面快照、Markdown）via 原样输出，各列的文本本身相同（mcpc 另有一层固定的外框），`github-find-code` 与 `playwright-docs-search` 里能看到。快照也比真实页面小得多。
- native 一列是「全部工具定义每轮完整注入」的朴素模型。支持工具延迟加载或检索的框架会大幅降低这一项，参考上面「native 不计注入」一行。
- 轮数：native 按「每个并行调用批次一轮，再加最后的回答一轮」；via、mcp2cli 与 mcpc 的每条命令各占一轮，不假设 agent 会把多条命令合并成一次 shell 调用。
- 没有计入模型自己写的思考和最终回答，也没有计入对话历史的累积（各种方式都有）；native 的每轮注入按未缓存计。
- 命令序列的选择有主观成分：mcp2cli 在工具不超过 25 个的 server 上用 `--list`，更大的用 `--search <关键词>`，每条要用的命令先看一次 `--help`（它的 skill 就是这样写的）；via 从 `via <provider>` 或 `via find` 开始（`via prompt` 的域摘要已说明有哪些 provider），资源视图的签名够写出调用时不再加 `-h`；mcpc 先 `connect`（输出就是该 server 的工具概览），每个有参数的工具先 `tools-get` 一次再 `tools-call`，参数写成 `key:=value`，结果用默认的人类可读输出（不加 `--json`，后者更长）。
- 为了可复现，元信息行里的耗时统一记为 `100ms`，端口和沙箱路径也做了归一。

### 与 [0.4-tokens](0.4-tokens.md)（#34 之前）相比

这一份是 [#34](https://github.com/modelctx-ai/via/issues/34)（`via find` 结果带 `example:` 行、资源视图签名带类型与枚举）以及 #30/#31/#32/#36 合并后重跑的，回放数据与任务集不变。目标是「find 之后不必再 `-h`」，所以逐个检查了命令序列里的每一条 `-h`：只有前一步（`via find` 或 `via <provider> <resource>`）的输出已经给出这条调用需要的全部信息才去掉，拿不准的保留，理由写在各任务 yaml 的注释里。

native 不变（382,379），via / native 仍是 4%；mcpc 的数字与旧结果相同；mcp2cli 合计 59,834 → 60,152 与 via 无关，是评测脚本在 mcp2cli 的说明里多写了一句「别名已经建好」（说明从 4,047 增到 4,083 token，每个任务各计一次）。

**没有任何一条 `-h` 能去掉，命令数没变，token 反而多了 634。** 逐条原因：

- **前一步不是 `find` 或资源视图（4 条）**：`notion search -h`、`playwright browser-type -h`、`cloudflare search -h`、`cloudflare execute -h` 面对的是叶子工具，前面只有 provider 视图（`via notion`、`via playwright`、`via cloudflare` 只列名字，没有签名）。`#34` 的改动只发生在 `find` 与资源视图上，所以这几条没有变化。
- **前一步是资源视图，但签名没有带上枚举（3 条）**：`github issue:read -h` 和 `github pull-request:read -h` 恰好是 `#34` 最想解决的 `method=get|get_comments|…` 的情形，但这两行的完整带类型签名超过 60 列，按规范退回了不带类型的写法（`method, owner, repo, issue-number, [page], [per-page]`），`method` 的取值仍看不到，资源视图又没有 `example:` 行。`notion page:update -h` 同理：`command` 是长枚举，连起来超过 60 个字符，不进签名；要用的 `insert_content_after` 只能在 `-h` 里确认。
- **本来就没有 `-h` 的任务（4 个）**：`github-find-code`、`linear-create-issue`、`linear-my-work` 靠资源视图的签名就能写出调用，`cross-issue-to-pr` 用 `via find` 找工具，两次结果里的 `example:` 已经给出写法，所以没有 `-h` 可去。

token 变化的来源：

- **`example:` 行的代价**：`cross-issue-to-pr` 的两次 `via find` 分别多 166 和 231 token（十条结果各多一行，平均约 198，比 CHANGELOG 里估的 170 略高），这是整个 +634 里最大的一项（+400 含 `via linear comment` 的 +2；各项按步取整，加起来与合计差几个 token）。这个任务没有 `-h` 可省，所以是净增加；`--brief` 可以关掉，但那样又得靠 `-h` 才知道写法。
- **`-h` 输出变长（+221）**：七条保留的 `-h` 各多 15–58 token，来自 [#36](https://github.com/modelctx-ai/via/issues/36)（`-h` 总是为每个必填参数列一行，没有描述的也单独成行），不是 #34；`-h` 的 `example:` 行 0.4 首次结果里就有。没有逐提交二分，归因依据是 CHANGELOG 与 `-h` 输出的对比。
- **资源视图的类型标注（+17）**：`issue-comment`、`pull-request`、`page` 等几行多了 `:num`、`:json`，合计十几个 token。

**这些数字说明什么**：#34 在这九个任务上没有省命令，也没有省 token，原因不是 `example:` 没用，而是基准里的路径几乎都不经过 `find` 之后的 `-h`：要么是叶子工具（`-h` 是唯一的签名来源），要么是带长枚举参数的资源视图（签名因为超过 60 列退回了旧写法）。想让「find 之后不必再 `-h`」在基准里显现出来，有两个方向，本次都没有做（它们不是「去掉一条 `-h`」，而是换了 agent 路径或改了规范）：把 `github-triage-bugs`、`github-pr-summary`、`notion-update-doc` 的路径改成 `via find "…"` 直接取得 `example: via github issue:read --method get …`，省掉 provider 视图、资源视图和 `-h` 三步，换来一次约 200 token 的 find；或者在资源视图里对超过 60 列的签名仍然保留枚举（例如 `method=get|…` 只对必填的枚举参数展开）。这需要先在 `docs/spec/discovery.md` 里改规范。
