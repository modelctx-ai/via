# 性能基准结果（0.3：冷启动、`find` 与 daemon 内存）

0.1 与 0.2 的基准有三项没有达到[性能目标](../../docs/development/testing.md#性能目标)：浏览类命令（`via`、`via <provider>`、`via find`）的冷启动、一千个工具上的 `find`、daemon 建立会话后的常驻内存。这份结果记录针对它们做的优化和复测。方法见[测试与评测](../../docs/development/testing.md#性能基准)；0.1 的数字见 [perf-0.1.md](perf-0.1.md)，Bun 单文件可执行见 [perf-0.3.md](perf-0.3.md)。

## 环境

- CPU：Intel Xeon @ 2.80 GHz，4 核（虚拟机），内存 15.7 GiB；Linux 6.18.44 x64，Node.js v22.22.0
- 场景同 0.1：8 个真实 `tools/list` 快照（180 个工具）写入磁盘缓存后 server 全部停止；HOME 与 TMPDIR 在临时目录里；`VIA_NO_DAEMON=1`（第 5 节除外）；每行预热 5 次、测 30 次
- **「改动前」是同一份源码去掉这批改动**：即 `claude/focused-faraday-hw84ya`（含 resources/prompts、同义词扩展、Windows、Bun 单文件）的构建，不是 0.1 的构建。第 1b 节用 `--compare` 与它交替运行；第 1、4、5 节用 `--dist` 在另一次运行里单独测它（第 5 节加 `--plain-daemon`，让 daemon 不带现在的 V8 与 malloc 设置）。
- **这台机器是共享的**，虚拟机的噪声很大：`node -e 0` 在不同运行里是 28–43 ms，p95 不可信。所以下面「减去 `node -e 0`」一列比墙钟更能反映 via 自己的耗时；改动前后不在同一次运行里的数字（第 1 节）只看量级，同一次交替运行里的数字（第 1b 节）才可以直接比。

## 结论

| 目标 | 改动前 | 改动后 | 结果 |
| --- | --- | --- | --- |
| 冷启动 `via`（根视图，缓存热，无 daemon） | 106.9 ms（比裸 node 多 71.8） | 73.6 ms（多 44.3） | 达到 |
| 冷启动 `via github` | 117.3 ms（多 82.2） | 77.3 ms（多 47.9） | 达到，余量小 |
| 冷启动 `via find` | 137.1 ms（多 102.1） | 80.1 ms（多 50.7） | 在目标线上（80.1 对 < 80），未稳定达到 |
| 冷启动 `--version` | 40.3 ms | 37.0 ms | 持平（噪声内） |
| 冷启动 经热 daemon 的 `via` / `via find`（交替运行） | 115.8 / 123.2 ms | 82.7 / 92.3 ms | 大幅改善，未达到 |
| 冷启动 带框架配置（4 个文件，含 71 KiB `.claude.json`）的 `via` / `via find` | 142.2 / 153.8 ms | 103.4 / 110.3 ms | 大幅改善，未达到 |
| 一千个工具上的 `find`（库路径，新进程：还原 + 索引 + 首次查询） | 80.7 ms（构建 + 索引 + 查询） | 21.3 ms | 达到（< 30 ms） |
| 一千个工具上的 `find`（整进程，交替运行） | 210.8 ms | 109.8 ms | 减半，未达到 80 ms |
| daemon 常驻内存（建立 HTTP / stdio 会话之后） | 91.9 / 88.8 MiB | 76.0 / 78.6 MiB | 达到，余量小（见下） |
| 热 daemon 额外开销 | 7.52 ms | 6.78 ms | 持平（达到） |

## 做了什么

每一项都是测过才留下的；输出逐字节不变（现有的快照与端到端测试不变，另有新缓存的失效测试）。实现说明见 [implementation.md](../../docs/development/implementation.md#03-的冷启动工作数据见-benchresultsperf-03-cold-startmd)。

| 优化 | 效果（进程内，一次实验，多次中位数） |
| --- | --- |
| Node 内置模块不经 ESM 门面（`fs`、`fs/promises` 经 tsup 插件改写；`node:process`、`node:tty`、`node:crypto`、`node:net` 不再在浏览路径上初始化；stdout/stderr 用 `fs.writeSync`） | 浏览命令初始化的 Node 内部模块从 132 个降到 79 个；`--version` 从 100 个降到 78 个；每个门面约 6–12 ms |
| 纯 JS 的 SHA-256（64 KiB 以内） | 去掉浏览路径上的 `node:crypto`（约 6 ms） |
| 预构建目录（拆分、分域、检索词存成 `.view.json`，头体分开） | 几百个工具的构建加索引从十几毫秒到几毫秒；一千个工具 80.7 到 21.3 ms |
| 原始 `tools/list` 缓存文件头部读取、工具数组惰性解析 | 浏览命令不再解析任何 schema |
| 配置解析缓存（YAML 只存结构与偏移）与合法 JSON 走原生 `JSON.parse` | 不再为 `config.yaml` 加载 YAML 库（约 10 ms）；`.claude.json` 不加载 `jsonc-parser` |
| 一次 `import()` 取齐浏览命令的模块；渲染流水线与 MCP 客户端不进浏览路径 | 加载的分块从 36 个 / 525 KiB 到 40 个 / 249 KiB，且不含任何库（改动前含 yaml） |
| ASCII 快路径分词、扁平倒排表、预算好的词频 | 分词 4.2–6.3 ms 到 2.2–2.5 ms |
| daemon：不在内存里保存解析后的列表，`list` 带 `have` 时不重传，`--max-semi-space-size=2` 与 `MALLOC_ARENA_MAX=2` | 建立会话后的常驻内存约 90 MiB 到 76–79 MiB（空闲不变，约 58 MiB） |

## 5. 热 daemon

| daemon 常驻内存 | RSS MiB（改动前 → 改动后） | 其中匿名 / 文件（改动后） |
| --- | --- | --- |
| 刚启动 | 58.0 → 57.6 | 13.2 / 44.8 |
| 一个 HTTP 会话与一次调用之后 | 91.9 → 76.0 | 27.8 / 48.6 |
| 再加一个 stdio 会话与一次调用之后 | 88.8 → 78.6 | 30.3 / 48.8 |
| 多次调用之后 | 75.2 → 75.8 | 27.4 / 48.8 |

文件部分（约 45–49 MiB）是 node 可执行文件本身映射进来的页，与别的 node 进程共享，不由 via 控制。热 daemon 上一次调用的额外开销 7.52 → 6.78 ms（目标 < 15 ms）。

## 没达到或余量小的项，以及原因

- **`via find` 的冷启动在线上**（80.1 ms 对 < 80）：比 `via` 多的约 6 ms 是索引加首次查询（含约 0.9 ms 的同义词表编译）。再往下要么缓存倒排表本身（体积随工具数增长，一千个工具约 1 MiB 的 JSON 要解析），要么让 daemon 常驻索引（协议要新增 `find` 请求，渲染得在两处实现），收益不抵复杂度，没有做。
- **经热 daemon 与带框架配置的场景仍高于 80 ms**：daemon 路径多一次连接、握手和 `list` 往返（每个 provider 一次，已经不传工具）；框架配置路径要读 71 KiB 的 `.claude.json`，并为 TOML（Codex）与带注释的 JSONC（VS Code）加载 `smol-toml` 与 `jsonc-parser`，两者各约 10 ms，而 TOML 与带注释的 JSONC 没有做解析缓存：TOML 库不给字符串的位置，要缓存就得复制字符串值，Codex 的配置里可能有字面量令牌，违反「缓存不含凭证值」。
- **一千个工具的整进程 `find`**（109.8 ms）：库路径只占 21 ms，其余是进程启动、50 个 provider 的缓存文件读取和渲染。
- **daemon 内存余量只有 1–4 MiB**：多次独立运行里，建立两个会话之后在 76–83 MiB 之间波动（本次最高 78.6）。MCP SDK 与 zod 在 daemon 里常驻约 16 MiB，无法去掉；`--max-semi-space-size=2` 与 `MALLOC_ARENA_MAX=2` 已经用上。

## 目标重新标定的建议（未改规范里的数字）

规范里的目标没有被悄悄改动，这里只是建议，由维护者决定：

1. **冷启动**：墙钟包含 `node` 自己的启动，而它在这台机器上就在 28–43 ms 之间浮动，不由 via 控制。建议把目标写成「比同机 `node -e 0` 多不超过 50 ms」（现在：`via` 44.3，`via <provider>` 47.9，`via find` 50.7），并把「经热 daemon」与「带框架配置」列为单独的、较宽的目标（建议 < 70 ms 与 < 80 ms，现在约 51 与 72–79 ms 之上）。
2. **一千个工具上的 `find`**：库路径（< 30 ms）已经达到，建议把目标明确写成库路径，整进程另列（建议比裸 `node` 多不超过 80 ms，现在约 78）。
3. **daemon 常驻内存**：RSS 里约 45–49 MiB 是共享的 node 二进制页。建议改用匿名内存（RssAnon，现在约 27–30 MiB）或把目标定为 RSS < 85 MB，而不是在 80 MB 线上留 1–4 MiB 的余量。
