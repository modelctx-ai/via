# 0025. 在配置里钉住授权服务器：`auth.oauth.issuer`

- 状态：已接受
- 日期：2026-10-22

## 背景

[ADR 0019](0019-oauth-client-identity-and-credentials.md) 把客户端凭据绑定到登录时发现的授权服务器：存储里有记录，才有东西可比较。两种场景它保护不了：

- **全新的机器**：CI 每次运行都是干净环境，存储里没有记录，凭据（机器授权的 secret 或私钥断言）发往受保护资源元数据**当时**指向的授权服务器——首次使用即信任。MCP server 被攻陷或被改写，就能让 via 把凭据发给别处（SEP-2352）。
- **用户本来就知道授权服务器是谁**：公司自己的 IdP、自托管的授权服务器。「首次使用即信任」把这个已知事实丢掉了。

ADR 0019 把「配置里钉死授权服务器」留作后续（路线图 e7）。

约束同 ADR 0019：不为特定 server 适配（[ADR 0007](0007-no-gateway-specific-adaptation.md)）；凭据不进输出（[security.md](../spec/security.md)）；CLI 冷启动不变。

## 决策

**新增 `servers.<name>.auth.oauth.issuer`：期望的授权服务器 issuer 标识。** 值是 RFC 8414 的 issuer：https 地址，没有查询串与片段，没有用户信息；`http` 只接受回环主机（本机开发与测试的授权服务器，与 `search.semantic.url` 同规则）。其他写法是 `invalid-field` 错误。授权码和 client credentials 两种授权都适用。

**发现到的授权服务器与钉住的不同就拒绝，在向它发出任何东西之前。** 「它的 issuer」取授权服务器元数据里的 `issuer`，没有元数据则为授权服务器的地址（与绑定用的同一个取法）。检查点：

- 登录：SDK 在发现之后、动态注册、授权请求、令牌请求之前调用 `clientInformation`，在这里比对（授权码流程的回调那一段同样经过）；
- 机器授权的登录与令牌请求、刷新：用发现结果（保存的或重新发现的）发出请求之前比对；
- 日常调用：保存的登录所属的 `issuer`（没有则取保存的发现结果）与钉住的不同，这条登录不再使用（连有效的 access token 也不用），`next: via auth logout <provider>`。

表现：退出码 4，`error: <provider>: its authorization server is <发现到的>, not <钉住的> as pinned by auth.oauth.issuer; nothing was sent to it`，`next: check auth.oauth.issuer of <provider> in your via config`（保存的登录不符时 `next: via auth logout <provider>`）。

**比较规则与绑定一致：忽略末尾的 `/`，其余逐字节相等。** RFC 8414 要求元数据里的 `issuer` 与取得元数据的地址精确相同，不做 URL 规范化（大小写、默认端口、百分号编码）；via 的绑定已经容忍末尾 `/`（实际的授权服务器常有这种不一致），钉住沿用同一个比较函数，不引入第二套规则。后果：钉住的值要照授权服务器元数据里的 `issuer` 写。

**钉住是附加条件，不替代绑定。** 两者都要满足：钉住的授权服务器不同于记录绑定的，仍按[绑定授权服务器](../spec/auth.md#绑定授权服务器)拒绝（需要 `via auth logout`）；先检查钉住，所以授权服务器与钉住的不同时看到的是钉住的错误。钉住不进存储键：同一个端点、`clientId`、`scopes` 共用一条记录，加上或改掉钉住后，已有的登录按上面的规则被接受或被拒绝。

**项目级配置可以写它，但不能改动或去掉用户配置里的钉住。** 理由：

- 钉住**只会让 via 拒绝**，从不让它多发一个字节：授权服务器永远由 MCP server 的元数据决定，配置里写什么都不能让凭据发往一个原本不会去的地方。所以项目级配置钉住一个攻击者的授权服务器，最坏是登录失败（拒绝服务，且错误信息点名 `auth.oauth.issuer`）；钉住合法的授权服务器是项目给协作者的保护。因此它和 `clientId`、`clientMetadataUrl`、`scopes` 一样，不属于改变传输的字段，不需要 `via trust`。
- 真正的风险是**放宽**：用户配置钉住了合法的授权服务器，仓库里的 `.via.yaml` 把它改成别的值或删掉（`auth` 在合并时整体替换，所以写一段不带 `issuer` 的 `auth.oauth` 就会去掉）。所以用户配置、用户级框架配置与 CLI 里设置的钉住，在项目级配置之后仍然有效：项目层的 `auth.oauth` 合并时沿用它，项目层写的 `issuer` 被忽略。用户配置里没有钉住时，项目层的钉住生效。
- 项目配置可以通过 `auth: none`、`bearer` 等换掉整个鉴权方式，这在此之前就是如此（OAuth 登录在鉴权方式换掉后不再被用），与钉住无关。

## 备选方案

- **字段名 `authorizationServer`**：与 `clientId`、`clientMetadataUrl` 同风格，但容易被读成「授权服务器的地址」（可以是发现用的 URL），而这里比较的是 issuer 标识；`issuer` 与 RFC 8414、存储里的 `issuer` 字段同名。
- **接受多个 issuer（列表）**：企业里授权服务器迁移时有用，但一个 server 同时用两个授权服务器是罕见的，先做单值，需要时可放宽成列表（单值仍合法）。
- **项目级配置禁止写**：更保守，但失去仓库给协作者统一钉住的能力（团队共享 `.via.yaml` 时，最适合放这个）；而它不能扩大 via 的发送范围，禁止没有换来安全。
- **项目级配置可以任意覆盖**：违反用户配置里钉住的意图，是真正的降级路径。
- **精确比较（不容忍末尾 `/`）**：与 RFC 字面一致，但与已有的绑定不一致，同一份配置里两处对同一个授权服务器的判断不同，更难解释。
- **钉住的值纳入存储键**：钉住变化时自动当作新登录，免去 `logout`；但改变存储键意味着旧记录成为孤儿，且「去掉钉住」会悄悄地多出一条登录，不如显式拒绝并提示。

## 后果

- 全新的 CI 机器上可以防住被改写的受保护资源元数据；`first use is trust` 的边界在写了 `issuer` 的 server 上不再成立。
- 授权服务器正常迁移（换域名）时，用户要同时改 `issuer`，并 `via auth logout`；这是预期的确认动作。
- 钉住的值写错（例如少了路径部分）时登录失败，错误信息显示发现到的值，照抄即可。
- 新增错误 `PinnedIssuerMismatchError`（`src/client/oauth/errors.ts`）；`src/config/merge.ts` 记录用户层的钉住。
- ADR 0019 里「留作后续」的备选方案由本 ADR 实现；ADR 0019 本身不被取代。
