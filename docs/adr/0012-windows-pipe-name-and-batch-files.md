# 0012. Windows：管道名由令牌派生，批处理文件拒绝而不转义

- 状态：已接受
- 日期：2026-10-20

## 背景

Windows 支持（路线图 c4）的核心是 Node 的 `net` 能直接使用 named pipe，daemon 的协议无需改动。剩下两个有取舍的问题：

1. POSIX 上 daemon 的防护是 socket 文件的属主与 0600 权限、目录 0700，加上握手令牌。Windows 没有这些模式位，Node 也取不到管道对端的 SID 或 pid。原先设想的 `\\.\pipe\via-<用户名>` 是固定的、可猜的名字：任何本地用户都能列出管道名，并在 daemon 退出后抢先创建同名管道，等 CLI 把握手令牌和请求参数交过去。
2. `npx`、`az` 等是 `.cmd` 垫片。Node 在 CVE-2024-27980 之后不再允许 `spawn` 在 `shell: false` 时启动它们；经 `cmd.exe` 又会让参数被重新解析（BatBadBut）。同时，Windows 的 `CreateProcess`、`cmd.exe` 和常见的 `which` 实现都优先搜索当前目录，而 stdio server 默认在可能不可信的仓库目录里运行。

## 决策

- 默认管道名为 `\\.\pipe\via-<用户名>-<SHA-256(令牌) 的前 128 位>`。令牌是 daemon 每次启动生成的随机数，写在用户缓存目录的 `via.token`；CLI 读令牌文件、算出名字、连接。没有令牌文件等于没有 daemon。握手令牌的校验与 POSIX 一致。
- Windows 上不做属主与权限位检查，也不引入原生依赖去取对端 SID；把这点和残留风险（用户目录 ACL 被放宽、管理员）写进规范。
- 命令名由 via 自己从 `PATH` 与 `PATHEXT` 解析，不找当前目录。`cmd:` 的 `.cmd` / `.bat` 经 `cmd.exe /d /v:off /s /c` 启动，每个词加双引号，含 `"`、`%`、换行、NUL 的参数直接拒绝。stdio server 沿用 MCP SDK 自带的 `cross-spawn` 启动，但 via 先解析出完整路径并做同样的参数检查。
- 打开浏览器改用 `rundll32 url.dll,FileProtocolHandler`，不再经 `cmd /c start`，且只打开 `http(s)`。

## 备选方案

- **固定管道名，只靠令牌**：令牌不会泄给没有读权限的人，但抢先占位的进程可以收到 CLI 发来的请求参数并伪造应答；派生名字把这个窗口关掉，代价是 CLI 必须先读令牌文件，且 `--socket` 需要单独处理（显式给出的名字原样使用）。
- **每个用户一个随机但固定的名字（密钥文件）**：名字在 daemon 重启之间不变，一旦被观察到，下一次启动前仍可被占位。
- **用 `icacls` 或 Win32 ACL 收紧文件权限、校验对端 SID**：需要起子进程或原生扩展，冷启动与分发成本不值得；用户目录的默认 ACL 已经满足同用户模型，残留风险写入规范。
- **转义参数而不是拒绝**：`cmd.exe` 对双引号和 `%` 没有可靠的转义写法，一个微妙的错误就是命令注入；用户可以改用 `.exe` 形式的命令。拒绝让问题在配置阶段暴露。
- **完全自己实现 stdio 子进程启动**：要替换 SDK 的 `StdioClientTransport`，维护成本远大于预先解析加检查。

## 后果

- 状态输出里 daemon 未运行时的 socket 显示为 `\\.\pipe\via-<用户名>-*`。
- daemon 在令牌文件被删或被别的 daemon 覆盖后自行退出。
- 用 `%` 或双引号做参数的 `.cmd` 命令在 Windows 上不能用；批处理文件内部如何使用参数不在 via 的保证范围内。
- 以后若引入原生扩展，可以补上管道对端 SID 校验，而不改变协议。
