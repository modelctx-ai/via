# 0010. `via find` 默认用确定性同义词扩展，embedding 检索是用户显式开启的可选项

- 状态：已接受
- 日期：2026-10-20

## 背景

`via find` 按规范写法三级匹配加 BM25 排序（[discovery.md](../spec/discovery.md#搜索)）。agent 的查询是自然语言，用词常与工具名不同：问「删除工单」，工具叫 `issue:delete` 或 `ticket:remove`；问「合并 PR」，工具叫 `pull-request:merge`。纯词法检索在这类查询上漏召回。discovery.md 把「语义检索」留作后续可选项；路线图 c2 要实现它。

约束：

- 「发现逻辑是确定性的，不调用模型」（AGENTS.md）。同一份目录、同一个查询，任何机器、任何时间输出相同，不依赖网络和密钥。
- 规则类内容放 `data/`，不写进代码；不为特定 server 写适配（[ADR 0007](0007-no-gateway-specific-adaptation.md)）。
- CLI 冷启动是核心指标，默认路径上不能多出可感知的开销。
- 工具描述和查询发给第三方是新的数据外流面，必须由用户明确同意。

## 决策

分两层，两层的确定性边界不同。

**第一层：确定性语义扩展，默认开启，不调用模型。**

- 概念与同义词写在 `data/synonyms.json`（JSON Schema：`data/schema/synonyms.schema.json`）：动词同义组（`remove`/`delete`/`destroy`/`drop`…）、资源同义组（`issue`/`ticket`、`pr`/`pull request`/`merge request`、`repo`/`repository`…）、简单词形还原的后缀规则（`creating` → `create`）。组内成员可以是多词短语。
- 只在**查询侧**扩展，索引不变：载入目录的开销不增加。查询里每个词按「词本身」与「同义词」中得分更高者计分，同义词乘以小于 1 的权重（动词 0.35，资源 0.6，词形还原 0.8），且其 IDF 不超过它所代表的查询词的 IDF，所以带原词的工具永远排在只带同义词的工具之前，罕见缩写也压不过它代表的常见词。
- 规范写法的三级匹配与并列规则**不变**：一到三级仍先于只命中 BM25 的工具，同一级内按分数、再按规范写法排序。扩展只改变第四级里的 BM25 分数。
- 口语填充词（`i`、`want`、`please`…）在查询侧丢弃，仍写在数据文件里。
- 评测：`test/fixtures/search/eval.json` 是 98 条自然语言查询到期望规范名的集合，`heldout.json` 是调参之后另写、从未用于调参的 30 条。回归测试断言扩展不降低 recall@1、recall@5、MRR，并锁定实测下限。

**第二层：可选 embedding 检索，默认关闭，只能在用户配置里开启。**

- `search.semantic: { provider: openai-compatible, url, model, auth, timeout, indexTimeout, dimensions }`，只读用户配置（和命令行覆盖）；项目配置与框架配置里的同名字段被忽略并告警，因为它会把工具描述与查询发往仓库指定的主机。`url` 必须是 https（本机回环地址可用 http）且不含内嵌凭证，`auth` 的值是凭证引用。
- 工具描述的 embedding 按文本哈希缓存在用户缓存目录（0700，文件 0600），每个（端点、模型、维度）一个文件；换了描述的工具才会重新请求。查询在 `find` 时即时 embedding。
- 排序：与 BM25 用 RRF（k = 60）融合，只作用于第四级；规范写法的三级匹配仍在最前。同一份缓存、同一个查询，结果相同。
- 严格超时（缓存完整时默认 3 秒，需要补 embedding 时默认 30 秒）；任何失败（超时、HTTP 错误、凭证缺失、响应格式不对、缓存不完整）都静默退回词法排序，只在 stderr 写一行 `· semantic unavailable: <原因> · lexical results`，退出码不变。原因不含响应体、请求头或端点。
- 只影响 `via find`；`via`、`via <provider>`、`via sync` 等不触碰它。代码是独立分块，只在配置了 `search.semantic` 时才加载，关闭时冷启动开销为零。
- 在 CLI 进程内完成，缓存在磁盘；不经 daemon（目录的拆分、分域、索引本来就在 CLI 侧计算，见 [daemon.md](../spec/daemon.md)）。

## 怎样与「发现逻辑是确定性的」相容

这条规则要保护的是：同一输入得到同一输出、离线可用、没有隐含的网络与费用、不把用户数据发给第三方。

- **第一层完全满足它**：纯数据加纯函数，没有模型，没有网络；同义词表是仓库里的 JSON，改动经评审、有回归测试，和动词表、分域词典一样。这是默认行为。
- **第二层不满足它的字面，所以把它限制成一个可审计的例外**：
  - 默认关闭，开启需要用户在自己的用户配置里写明端点、模型与凭证，项目配置与框架配置都不能开启它；
  - 对给定的缓存与模型输出是确定的（RRF 的排名以规范写法打破并列），可复现；模型更换或端点升级导致的变化由用户自己选择承担；
  - 失败时退回第一层，`find` 不会因为它而失败或变慢超过超时；
  - 范围只有 `find` 的第四级排序：命名拆分、分域、浏览视图、规范写法依旧只由确定性规则产生（[ADR 0005](0005-command-grammar-provider-resource-verb.md)、[ADR 0006](0006-domain-is-a-view.md) 不受影响）。
- AGENTS.md 的这条规则因此改写为「发现逻辑默认确定性、不调用模型；唯一的例外是用户显式开启的 `search.semantic`（ADR 0010）」。

## 备选方案

- **索引侧扩展**（把同义词写进倒排索引）：每次载入目录都要付出构建时间与内存，且改动同义词表要重建；查询侧扩展零载入成本。
- **在 BM25 之外对同义词命中另设一级**：会改变规范的三级加 BM25 结构；现在的做法只调整第四级内部的分数。
- **本地小模型 / 内置向量**：需要打包几十 MB 的模型或原生依赖，违背冷启动与零新增依赖；同义词表在 fixture 上已拿到大部分收益。
- **默认开启 embedding**：破坏确定性与隐私默认值，也要求所有用户有端点与密钥。
- **每次 `find` 重新 embedding 全部工具**：1,000 个工具要几十次请求；按文本哈希缓存后，稳态只剩一次查询请求。
- **用 daemon 常驻 embedding**：目录在 CLI 侧计算，daemon 不持有工具描述的拆分结果；磁盘缓存读取（二进制，1,000 个 1,536 维向量约 6 MB）已经够快，不值得为此扩展协议。
- **把 embedding 配置放进项目配置**：仓库能让工具描述与查询流向任意主机，违反[信任模型](../spec/security.md#项目级配置的信任)。

## 后果

- 查询侧扩展让 `find` 在 fixture 目录上的召回明显提高（见 CHANGELOG 与 `npm run eval:search`），代价是 1,000 个工具上单次查询的中位耗时约 0.3 ms（此前约 0.2 ms），首次查询多一次约 1 ms 的同义词表编译。
- 同义词表是新的需要维护的数据：词组应当是通用英文与开发工具里的常识，而不是针对某个 server 的补丁（[ADR 0007](0007-no-gateway-specific-adaptation.md)）。新增或修改词组时运行 `npm run eval:search`，不得降低评测指标。
- 同义词扩展不改变任何规范名，因此 CHANGELOG 的「影响规范写法」一节不受影响。
- 开启 embedding 后，工具名、描述与参数名以及每次的查询会发往配置的端点；文档（security.md）如实写明，由用户决定。
- 缓存按文本哈希而不是按整份目录的哈希：目录里只有一个工具变化时，只重新请求这一个。缓存超过 20,000 条时丢弃本次未用到的条目。
