# 0032. `via servers add`：via 只在有人确认时写自己的用户配置，凭证只写引用

- 状态：已接受
- 日期：2026-11-13

## 背景

框架里没有配过的 server，以及凭证，只能手改 `~/.config/via/config.yaml` 才能加进 via。via 自己从不写这个文件：能读框架配置（[ADR 0003](0003-read-only-framework-configs.md)）掩盖了这一点，但第一次用、或者要加一个只给 via 用的 server 时，用户面对的是一份要自己查字段的 YAML。空配置的提示也只能说「把它加进某个文件」。

加一条命令并不难，难的是它带来的三件事：

- **命名**。内置子命令名是保留字，新增一个顶层命令会让恰好叫这个名字的 server 必须改名（[cli.md](../spec/cli.md#内置子命令)）。
- **谁能运行**。agent 与 via 同一个用户、同一个 shell。它本来就能运行任何命令，但「agent 自己往配置里加了一个 server」会留在配置里，之后每个会话都带着它；项目级配置为此要 `via trust`，用户配置没有这道关。
- **凭证**。最顺手的写法是 `--bearer <令牌>`，而配置里只该有引用（[security.md](../spec/security.md)）：令牌写进文件，`via doctor` 事后告警也已经晚了，它还留在 shell 历史里。

## 决策

1. **命令是 `via servers add`**，`servers` 的子命令，不新增保留字。两种写法：
   - `via servers add <name> <url> [--bearer <引用> | --oauth] [--header <名>=<值>]…`
   - `via servers add <name> [--env <键>=<值>]… -- <命令> [参数…]`

   `--` 之后是 server 的命令行，原样保留：其中的 `-h`、`--yes`、`-o` 不被 via 当作全局选项。这条透传只对 `via servers add` 生效，其他命令里全局选项仍然可以出现在任何位置。
2. **只有终端前的人能让它写入**，与 `via trust` 相同的界线。命令先打印将要写入的那几行 YAML，再问 `[y/N]`；不是 `y`/`yes` 就不写。没有终端（agent 经 shell、`via batch`、管道）时退出码 5，`next:` 让 agent 请用户自己运行。`--yes` 不能代替确认，也没有环境变量开关：脚本化的安装直接写 YAML。`--dry-run` 只打印不写，不需要终端。`via serve` 不暴露它。
3. **凭证只接受引用**。`--bearer` 的值必须是 `env:`、`keychain:`、`file:`、`cmd:` 之一。`--header`、`--env` 的键名像是秘密时（与 `via doctor` 判定明文凭证用同一个规则：`KEY`、`TOKEN`、`SECRET`、`PASSWORD`、`AUTH`、`CREDENTIAL`），值也必须是引用；其余的键可以写普通值。URL 里带 userinfo、或查询参数名像是秘密的，同样拒绝。被拒绝的值不在任何输出里重复。结果是：这条命令写出的东西，`via doctor` 不会报明文凭证。
4. **只新增，不修改**。名字已经被任何来源的 server 占用（用户配置、项目配置、框架配置，按 provider 名归一化后比较；被 `disabled` 的也算）时拒绝，并指向要改的那一处。给框架里已有的 server 补凭证仍然手写覆盖层。名字不能是内置子命令名。
5. **不动文件里别的字节**。新条目按现有缩进插在 `servers` 块的末尾（没有 `servers` 就追加一块），注释、空行、别的键原样保留；文本里没有可插的位置时（`servers: {}`、空的 `servers:`）才由 YAML 库重写整份文档。无论哪种，写之前把结果重新解析，与「原来的内容加上这一条」逐项比较，不相等就不写。文件是符号链接时写到它指向的文件；先写临时文件再改名；新文件权限 0600，已有文件保持原权限。文件本身不是合法 YAML、或顶层与 `servers` 不是映射时拒绝，不尝试修复。
6. **沙箱里拒绝**。开启了 `sandbox` 时配置目录在沙箱里只读（[ADR 0027](0027-run-via-inside-a-sandbox-program.md)），命令说明原因并让用户在沙箱外运行（把 `servers` 写进 `sandbox.exclude`）或手工添加，不为它开例外。

## 备选方案

- **顶层的 `via add`**：更短，但 `add` 成为保留字；`via servers add` 多打一个词，换来不影响任何现有配置。
- **允许 `--yes` 或环境变量跳过确认**（`via trust` 有 `VIA_ALLOW_NONINTERACTIVE_TRUST`）：`via trust` 的非交互用法是为 CI 里检出仓库后放行已审过的配置，没有别的办法；这里有，写 YAML 就行，所以不留口子。
- **接受令牌并替用户存进钥匙串**（`--bearer` 后面提示输入，写成 `keychain:` 引用）：是更完整的上手体验，但要多一条录入与存储秘密的路径（各平台钥匙串、不可用时的退路、撤销）。这次不做；引用的四种写法在用法行里列出。
- **同名时合并成覆盖层**（给框架里已有的 server 加 `env`）：这是「修改」而不是「添加」，要回答覆盖哪一层、与框架那边改动的先后，以及怎样向确认的人展示合并后的结果。留给以后的 `set` 一类命令。
- **用 YAML 库直接重写文档**：实现最短，但会挪动行尾注释、改写流式序列里的空格，用户手写的文件每加一条就变一次样。
- **沙箱里自动改到沙箱外执行**：等于让一条命令决定自己不受沙箱约束；`exclude` 本来就是用户用来做这个决定的地方。

## 后果

- 上手多了一条不用查字段的路：空配置的提示、`via servers -h`、快速上手都指向它。
- via 第一次写自己的用户配置。写入路径只有这一条，并且有人确认、有语义校验；`AGENTS.md` 里「不写入任何 agent 框架的配置文件」不变。
- 给已有 server 补凭证、删除 server、改名仍然要手改文件；秘密的录入仍然在 via 之外（环境变量、钥匙串工具）。
- `--` 在 `via servers add` 里有了含义。其他命令不受影响，测试钉住这一点。
- agent 看到空配置的提示后可能尝试运行它，得到的是退出码 5 和「请用户在终端运行」：与 `via trust` 一致，不需要改给 agent 的说明。
